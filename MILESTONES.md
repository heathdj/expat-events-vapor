## M5 — Realtime chat — ✅ done (build + test + human-reviewed server checkpoint; one bug found and fixed along the way)

`ChatMessage` model, its migration, and the `ChatMessageDTO`/`ChatEnvelope` wire types already existed from M1/the shared package. Mapping to the plan's 6 acceptance criteria (§M5):

1. Two concurrent sessions both seeing a message live, without reload — ✅ human-verified: two browser windows (one normal, one incognito) on the same event's chat, each signed in, both saw the other's message appear immediately with no reload. Not automatable — XCTVapor has no WebSocket test client wired into this suite — so this stayed a server-checkpoint item, the same way M2's OAuth click-through was.
2. Messages persist to `ChatMessage`, reload shows the same history — `testChatServiceSendPersistsMessageWithSenderDisplayInfo` (send persists) and `testChatServiceHistoryReturnsMessagesOldestFirst` (history read-back, oldest first) at the service level; `testChatUIRendersWithAndWithoutHistory` confirms the page itself renders that history into `#chat-messages` on load, both with messages and empty. ✅ (service + render layer; the "live view showed it, then a reload shows the same thing" round-trip specifically is part of the item-1 checkpoint.)
3. Replies store `parentID` and render nested; a reply-to-a-reply is rejected (one level only) — `testChatServiceRejectsReplyToAReply`, plus `testChatUIRendersWithAndWithoutHistory` asserting the `ml-6 border-l-2` nested-indent class actually appears for a reply. ✅
4. An unauthenticated visitor cannot open a chat socket — enforced by `User.guardMiddleware()` on the route group, same pattern as `EventWebController`'s write routes. ✅ (route-level; not independently unit-testable beyond confirming the guard is in place, since it's the same proven middleware M2/M4 already rely on.)
5. A non-member of a private group event's hosting group cannot open that event's chat socket, even knowing the event id — `testChatServiceRejectsAccessToPrivateGroupEventForNonMembers` (covers a signed-in non-member and a fully anonymous requester, both rejected with `not_found`, reusing `EventService.assertVisible` exactly like the event page itself). ✅ at the service/authorization layer; `ChatWebController.assertCanOpenSocket` calls this same check inside `shouldUpgrade` before any socket upgrades.
6. Reload after disconnect still shows full history — ✅ human-verified after a real bug and fix (see below): a plain page reload re-fetches and re-renders the full history server-side (`EventWebController.detail`), which alone satisfies this criterion. `ChatWebController.handle` no longer *also* replays history over the socket on connect (it originally did; see the bug below for why that was wrong).

**Scope decisions made along the way:**
- **Web/HTML only, not `ChatEnvelope`/JSON.** The architecture doc documents `ChatEnvelope` as the wire format for a future native/SwiftUI socket client, while explicitly describing the web path as htmx-HTML-swap with no hand-written JS. Since M5's stated deliverables only cover the web client, `ChatRoomRegistry` broadcasts pre-rendered Leaf HTML (`String`), not `ChatEnvelope` JSON. A native/`/api/v1` JSON WebSocket endpoint is explicitly out of scope here, not half-built.
- **No click-to-reply UI.** Reply threading is fully implemented and tested server-side (`ChatService.send`'s `parentID`/depth check), and a reply renders correctly nested once it exists, but the compose form has no UI affordance to start one yet — a small, explicit scope trim in the same spirit as M4's city/venue autocomplete, not an oversight.
- **`shouldUpgrade` rejection's exact HTTP response is unverified.** `ChatWebController.assertCanOpenSocket` throws (via `Abort`/`APIError`) to reject an upgrade for an unauthenticated or unauthorized caller; what a real client actually observes (status code, whether the connection even completes far enough to see one) hasn't been confirmed against a live socket client, similar in spirit to the pre-existing 500-vs-404 web-path gap tracked above under M4. What's certain either way: the socket never upgrades, so no history and no broadcast ever reach a rejected caller. Worth checking at the same human server-checkpoint as item #1.

**Bug caught during self-review before any build**: `EventWebController.detail()`'s new `chatHistory` mapping had `try chatMessages.map { try bash.toDTO() }` — a stray leftover identifier instead of `$0` — from authoring the file through a shell heredoc. Caught by re-reading the file fresh rather than trusting the write, fixed to `$0.toDTO()`, and swept the rest of the new/edited files for the same class of mistake (none found elsewhere).

**Bug found at the human server-checkpoint (not caught by any test) and fixed**: every chat message appeared twice after a plain browser reload. Root cause: `ChatWebController.handle` replayed the event's full chat history over the socket on every connect — reasoning, at the time, that a client reconnecting *without* a full page reload should still see the complete thread. But htmx's `ws-connect` opens a fresh socket on every full page load, and `EventWebController.detail` had *already* rendered that same history straight into the page for that same load — so the replay duplicated every message on every ordinary reload, not just the rare drop-and-reconnect case it was meant for. Fixed by removing the replay entirely: the page's own server-rendered history already satisfies acceptance criterion #6 on its own, and this app has no in-page reconnect-without-a-full-reload path that would have benefited from the replay in the first place. Re-verified: `swift build`/`swift test` clean, and the human checkpoint's reload step re-run confirmed messages now appear exactly once.

**All M5 acceptance criteria verified**: `swift build`/`swift test` clean (21 tests, 0 failures) and the human server-checkpoint confirmed live two-session broadcast, private-group-event chat rejection, and (after the reload-duplication fix above) correct single-copy history on reload. **Still open, not blockers**: the `shouldUpgrade`-rejection's exact HTTP response is still unconfirmed against a real client (see `ChatWebController`'s own doc comment); the post-login-redirect gap tracked under M2; the narrow "message sent during the connect window" gap noted in `ChatService`'s doc comment; and, per the incremental-design-system decision, only plain Tailwind utility classes are used in this milestone's chat UI — not yet the design canvas's specific token/component system from `docs/design-system.md`, which remains an open incremental item for this and future milestones.

**Scope decisions made along the way** (mirroring the plan's own explicit scope, not oversights):
- **No "request to join" workflow for `.inviteOnly` groups.** `GroupService.join` rejects with a distinct `invite_only` error code rather than silently no-op'ing; the plan doesn't list this workflow as an M6 deliverable, and the group directory itself only ever lists `.public` groups (an invite-only group nobody can self-serve-join would just be a dead end to list). A direct link to an invite-only group's detail page still works for whoever already has the URL.
- **No ownership-transfer flow, so an owner cannot leave their own group.** `GroupService.leave` rejects this with a distinct `owner_cannot_leave` error code. Building transfer-of-ownership isn't in this milestone's deliverables, and letting an owner leave without one would either orphan the group or silently misrepresent its ownership.
- **Every role-based/enum-based Leaf conditional is a precomputed `Bool`** (`isOwner`, `canJoin`, `isPromotable`, ...), never an in-template comparison against an enum's raw value. Grepped the entire existing `.leaf` corpus before writing any M6 template and found no precedent anywhere for `#if(x == "y")`-style equality — rather than introduce the first use of an unproven syntax in this codebase, `GroupWebController` computes all of these booleans in Swift and the templates just branch on them.

**Real, pre-existing bug found while writing this milestone's tests (not introduced by this milestone) and fixed**: `EventAPIController`'s `GET` routes (`list`, `detail`) sat completely outside any authenticator in the route-group chain — not even an optional one — so `req.auth.get(User.self)` was always `nil` on those routes regardless of whether a valid Bearer token was sent. This has been true since M4; the write routes always had `UserBearerAuthenticator()` correctly applied. Impact was over-restrictive, not a security leak: a real group member using the API with a valid token to view a private group-hosted event would always be treated as anonymous by `EventService.assertVisible` and rejected, never wrongly granted access — same bug *class* as the M2 issue already tracked elsewhere in this document (a route sitting outside an authenticator entirely, not just outside a guard). Fixed by adding an `optionallyAuthenticated` route group (`UserBearerAuthenticator()` alone, no `guardMiddleware`) ahead of the existing `authenticated` group, and moving the two `GET` routes onto it. Confirmed safe by reading `UserBearerAuthenticator`'s own implementation: it never throws on missing/failed verification on its own, and Vapor's `BearerAuthenticator` middleware only invokes it at all when an `Authorization: Bearer` header is present — so applying it unconditionally can't newly reject anyone who was working before. Caught by, and now pinned down by, `testPrivateGroupEventVisibleToMemberViaAPINotToOutsider`.

**Seed data**: the seed command now creates a 4th user (Dana Kowalski, Premium), a 2nd group ("Foodies Lisbon", owned by Dana, Bob as a member), and a 3rd event ("Lisbon Food Crawl", hosted by that group) — 4 users, 2 groups, 3 events total — specifically so criterion #7's "at least 2 seeded groups" and group membership/roles/group-hosted events all have real data to click through by hand, not just synthetic rows created inline by tests.

**Bugs found by the real `swift build`/`swift test` run (none caught by self-review beforehand) and fixed**:
- **Build error, 11 call sites**: `.filter(\.$group.$id == try group.requireID())` — Swift doesn't allow `try` on the right-hand side of a non-assignment operator. Fixed by hoisting `let groupID = try group.requireID()` once per function and referencing that local in the comparison instead, across `GroupService` (7 sites) and this milestone's own new tests (4 sites, found by proactively grepping for the same pattern right after the compiler caught the first batch).
- **Test-process crash (signal 5, not a normal assertion failure)**: `testGroupDetailPageRendersThreeTabsWithDistinctContentForTwoGroups` called `toDTO` directly on the `Group` object `createGroup(_:ownerID:)` returns, which never eager-loads `$owner` (only `find(_:)`/`find(slug:)`/`publicGroups()` do, per `toDTO`'s own doc comment) — FluentKit's own eager-load guard fired: "Parent relation not eager loaded". Production code never hits this (`GroupWebController.create()` redirects to `/groups/:slug`, which re-fetches through `find(slug:)`); the test had skipped that re-fetch. Fixed by having the test re-fetch through `find(_:)` itself, matching the real request path instead of shortcutting around it.
- **Stale assertion**: `testSeedCommandIsIdempotent` hardcoded `groupCount == 1` from before this milestone's seed-data change added a 2nd group; updated to 2.
- **Wrong expected HTML-escape sequence, not a real rendering bug**: two assertions checked for an apostrophe escaped as `&#x27;`; reading LeafKit's own `String+HTMLEscape.swift` directly showed it escapes `'` as `&#39;` — the About-tab text was rendering correctly the whole time, the test's expected string was wrong. Fixed both assertions.
- **Test violated the very rule it wasn't testing**: `testGroupJoinIsIdempotentAndInviteOnlyGroupRejectsJoin` tried to have one Premium user own both a public and an invite-only group in the same test, tripping `PlanLimitsService.assertCanCreateGroup`'s one-group-per-membership rule (criterion #2, working as intended) on the second `createGroup` call.

## M2 — Auth: Apple + Google — ✅ done on Google (PR #4 merged); Apple's live verification deliberately deferred to M13

- `/login` offers Apple/Google only, no password field. ✅ (`pages/login.leaf`)
- New sign-in creates one `User` + one `OAuthIdentity`; a second provider on the same verified email links to the same `User` (`AuthService.findOrCreateUser`). ✅
- Session cookie (web) via `User.sessionAuthenticator()` / Fluent sessions. ✅
- **Real click-through bug, found and fixed (2026-09-10)**: after confirming Google sign-in worked end-to-end, a human server checkpoint caught that the nav never flipped to the signed-in state (no "Sign out") — `GET /events`/`GET /events/:id` sat entirely outside `User.sessionAuthenticator()`, so `req.auth.get(User.self)` was always `nil` there regardless of a valid session cookie, and `isSignedIn` was hard-wired `false`. Fixed by moving those two routes onto a session-authenticated-but-not-guarded route group in `EventWebController` (signed-out visitors can still browse). Covered by new test `testSignedInSessionFlipsEventsNavToSignedInState`, which constructs a real Fluent session record and round-trips it through an actual HTTP request rather than calling the handler directly — the earlier fragment-render tests wouldn't have caught this class of bug since they bypass routing/middleware entirely. Re-verified in a real browser after the fix: signed-in nav now shows "Sign out", and clicking it actually signs out.
- Bearer token (API) via `UserJWTPayload` + `UserBearerAuthenticator`; `POST /api/v1/auth/apple`/`/google` → `GET /api/v1/me`. ✅
- Invalid/expired provider token → structured 401 via `APIErrorMiddleware`, never a 500. ✅ (untested against real tokens)
- Sign-out invalidates the web session (`/logout`). ✅
- **Note for future milestones**: the human server checkpoint for this fix required a `migrate --yes` re-run because `_fluent_sessions` didn't exist in the dev Postgres — most likely the local dev database got reset at some point (a Docker/host restart) since it was last migrated+seeded. That re-migrate also meant the seeded demo events were gone (re-run `swift run App seed` to get them back) — not a bug, just a reminder that the local dev DB isn't assumed durable, so a missing-relation error there means "re-run migrate", not "something's broken."
- **Deliberate scope decision (2026-09-09)**: Sign in with Apple JS requires a verified HTTPS domain in its Services ID's Web Authentication Configuration — it does not accept `localhost`, and `expatevents.net` currently points at Firebase Hosting (per the plan's own §2 prerequisites; DNS doesn't move to this build until M13). Rather than standing up a throwaway tunnel domain just to unblock local testing now, **Apple-specific configuration and end-to-end verification are moved to M13** (Deployment), once the real staging/production domain exists to register. `APPLE_CLIENT_ID` support, `AppleIdentityTokenVerifier`, and the Sign in with Apple JS wiring in `login.leaf` are already built and code-reviewed — this defers *testing them for real*, not the code itself, and M13's acceptance criteria gain an explicit item for it (see below). Google has no such constraint (`localhost` is an allowed JavaScript origin), so **M2 proceeds now on Google alone**: `GOOGLE_CLIENT_ID` has been provided, and end-to-end verification is done — a real browser sign-in via Google, session cookie created, nav correctly reflects signed-in/out state, sign-out works. (`/api/v1/me` via the bearer-token path is still only code-reviewed/unit-tested, not manually curled — noted below.)
- PR #2's independent review flagged that no unit test exists for `AppleIdentityTokenVerifier`/`GoogleIdentityTokenVerifier`. Added `testGoogleIdentityTokenVerifierRejectsInvalidToken` (a garbage token is rejected as `.invalidProviderToken` via a real round trip to Google's `tokeninfo` endpoint). ✅ for Google; the equivalent for `AppleIdentityTokenVerifier` is still open, tracked with the rest of Apple's verification under M13.
- **Independent review of this fix flagged a real but currently-unreachable gap, tracked for M10**: fixing the nav bug also means `requesterID` now correctly flows into `EventWebController.detail()`'s `assertCanManage` check for signed-in visitors (previously silently always-false/anonymous — a bigger dormant side effect of the same bug than the nav alone). Neither `EventService.assertCanManage` nor `assertVisible` checks `User.isSuspended`, so a suspended host would now see "manage" controls on their own event's detail page that `NotSuspendedMiddleware` would then reject on submit (the write path itself stays safe — this is a UX inconsistency, not a security hole). Not fixed here because `isSuspended` isn't enforceable anywhere yet — M10 (Admin) is the milestone that actually introduces a way to suspend a user — so a proper fix belongs there, applied consistently across `EventService` (shared by both `EventWebController` and `EventAPIController`), not patched narrowly in this PR. Added `testSignedInHostSeesManageControlsOnEventDetailPage` to pin down the now-correctly-restored (non-suspended) case so this doesn't regress before M10 addresses suspension.

- **Found during M5's human server-checkpoint (not yet fixed, tracked here)**: signing in from an event detail page's "Sign in to join the chat" link drops you on `/events` afterward, not back on the event you were looking at — both `AuthWebController.signInWithApple` and `signInWithGoogle` hardcode `req.redirect(to: "/events")`. The fix is the standard pattern: `loginPage` accepts a `redirect` query param, `login.leaf` carries it through the `/login/apple`/`/login/google` POST bodies, and the two sign-in handlers redirect there instead — validated as a same-origin relative path (starting with a single `/`, not `//`) rather than trusted as-is, to avoid turning this into an open-redirect. Every `href="/login"` link (`base.leaf`'s nav, `event-detail.leaf`, `event-fragment.leaf`) then needs `?redirect=<current path>` appended. Small and self-contained, but touches the auth flow rather than anything chat-specific, so it's tracked here for its own small commit/PR rather than folded into M5's.

## M5 — Realtime chat — ✅ done (build + test + human-reviewed server checkpoint; one bug found and fixed along the way)

`ChatMessage` model, its migration, and the `ChatMessageDTO`/`ChatEnvelope` wire types already existed from M1/the shared package. This branch adds the actual realtime path: `ChatRoomRegistry` (an actor holding live sockets, keyed by event then connection), `ChatService` (persistence + connect/send-time authorization, mirroring `EventService`'s "one service, both surfaces" shape), `ChatWebController` (the WebSocket route), and the htmx `ws`-extension chat UI on `pages/event-detail.leaf`.

Mapping to the plan's 6 acceptance criteria (§M5):

1. Two concurrent sessions both seeing a message live, without reload — ✅ human-verified: two browser windows (one normal, one incognito) on the same event's chat, each signed in, both saw the other's message appear immediately with no reload. Not automatable — XCTVapor has no WebSocket test client wired into this suite — so this stayed a server-checkpoint item, the same way M2's OAuth click-through was.
2. Messages persist to `ChatMessage`, reload shows the same history — `testChatServiceSendPersistsMessageWithSenderDisplayInfo` (send persists) and `testChatServiceHistoryReturnsMessagesOldestFirst` (history read-back, oldest first) at the service level; `testChatUIRendersWithAndWithoutHistory` confirms the page itself renders that history into `#chat-messages` on load, both with messages and empty. ✅ (service + render layer; the "live view showed it, then a reload shows the same thing" round-trip specifically is part of the item-1 checkpoint.)
3. Replies store `parentID` and render nested; a reply-to-a-reply is rejected (one level only) — `testChatServiceRejectsReplyToAReply`, plus `testChatUIRendersWithAndWithoutHistory` asserting the `ml-6 border-l-2` nested-indent class actually appears for a reply. ✅
4. An unauthenticated visitor cannot open a chat socket — enforced by `User.guardMiddleware()` on the route group, same pattern as `EventWebController`'s write routes. ✅ (route-level; not independently unit-testable beyond confirming the guard is in place, since it's the same proven middleware M2/M4 already rely on.)
5. A non-member of a private group event's hosting group cannot open that event's chat socket, even knowing the event id — `testChatServiceRejectsAccessToPrivateGroupEventForNonMembers` (covers a signed-in non-member and a fully anonymous requester, both rejected with `not_found`, reusing `EventService.assertVisible` exactly like the event page itself). ✅ at the service/authorization layer; `ChatWebController.assertCanOpenSocket` calls this same check inside `shouldUpgrade` before any socket upgrades.
6. Reload after disconnect still shows full history — ✅ human-verified after a real bug and fix (see below): a plain page reload re-fetches and re-renders the full history server-side (`EventWebController.detail`), which alone satisfies this criterion. `ChatWebController.handle` no longer *also* replays history over the socket on connect (it originally did; see the bug below for why that was wrong).

**Scope decisions made along the way:**
- **Web/HTML only, not `ChatEnvelope`/JSON.** The architecture doc documents `ChatEnvelope` as the wire format for a future native/SwiftUI socket client, while explicitly describing the web path as htmx-HTML-swap with no hand-written JS. Since M5's stated deliverables only cover the web client, `ChatRoomRegistry` broadcasts pre-rendered Leaf HTML (`String`), not `ChatEnvelope` JSON. A native/`/api/v1` JSON WebSocket endpoint is explicitly out of scope here, not half-built.
- **No click-to-reply UI.** Reply threading is fully implemented and tested server-side (`ChatService.send`'s `parentID`/depth check), and a reply renders correctly nested once it exists, but the compose form has no UI affordance to start one yet — a small, explicit scope trim in the same spirit as M4's city/venue autocomplete, not an oversight.
- **`shouldUpgrade` rejection's exact HTTP response is unverified.** `ChatWebController.assertCanOpenSocket` throws (via `Abort`/`APIError`) to reject an upgrade for an unauthenticated or unauthorized caller; what a real client actually observes (status code, whether the connection even completes far enough to see one) hasn't been confirmed against a live socket client, similar in spirit to the pre-existing 500-vs-404 web-path gap tracked above under M4. What's certain either way: the socket never upgrades, so no history and no broadcast ever reach a rejected caller. Worth checking at the same human server-checkpoint as item #1.

**Bug caught during self-review before any build**: `EventWebController.detail()`'s new `chatHistory` mapping had `try chatMessages.map { try bash.toDTO() }` — a stray leftover identifier instead of `$0` — from authoring the file through a shell heredoc. Caught by re-reading the file fresh rather than trusting the write, fixed to `$0.toDTO()`, and swept the rest of the new/edited files for the same class of mistake (none found elsewhere).

**Bug found at the human server-checkpoint (not caught by any test) and fixed**: every chat message appeared twice after a plain browser reload. Root cause: `ChatWebController.handle` replayed the event's full chat history over the socket on every connect — reasoning, at the time, that a client reconnecting *without* a full page reload should still see the complete thread. But htmx's `ws-connect` opens a fresh socket on every full page load, and `EventWebController.detail` had *already* rendered that same history straight into the page for that same load — so the replay duplicated every message on every ordinary reload, not just the rare drop-and-reconnect case it was meant for. Fixed by removing the replay entirely: the page's own server-rendered history already satisfies acceptance criterion #6 on its own, and this app has no in-page reconnect-without-a-full-reload path that would have benefited from the replay in the first place. Re-verified: `swift build`/`swift test` clean, and the human checkpoint's reload step re-run confirmed messages now appear exactly once.

**All M5 acceptance criteria verified**: `swift build`/`swift test` clean (21 tests, 0 failures) and the human server-checkpoint confirmed live two-session broadcast, private-group-event chat rejection, and (after the reload-duplication fix above) correct single-copy history on reload. **Still open, not blockers**: the `shouldUpgrade`-rejection's exact HTTP response is still unconfirmed against a real client (see `ChatWebController`'s own doc comment); the post-login-redirect gap tracked under M2; the narrow "message sent during the connect window" gap noted in `ChatService`'s doc comment; and, per the incremental-design-system decision, only plain Tailwind utility classes are used in this milestone's chat UI — not yet the design canvas's specific token/component system from `docs/design-system.md`, which remains an open incremental item for this and future milestones.
